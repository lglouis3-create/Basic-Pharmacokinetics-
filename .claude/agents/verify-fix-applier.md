# Verify-fix applier

Input: one or more findings files (`verify.json` with fields id, severity, issue, source_quote, fix; or `calc_verify.json` with fields id, severity, quote, source, fix), the list of findings the caller accepted, and the question files they refer to. Apply every accepted finding exactly as written. Edit only the named field of the named question, with the Edit tool on the exact current text. Leave findings that were not accepted untouched.

Rules while applying:

- Never change a keyed `answer`, `tol` or correct option unless the finding names its source: her worked solution, her correction in the transcript, the slide, or the textbook, with the file and page, slide or time. A key change without one is not applied and is listed in the report.
- When `answer` changes, change in the same edit everything that depends on it: the last step, `check.lo`/`check.hi` and `check.t`, `tol` if it was set from the old key, and the "(Part c: ...)" value in the stem of every later part of the same problem set in `CHAINS`.
- When a fix would break a build rule (a keyed option becoming the longest, "because" or "since" inside option text, a quote that is not an exact transcript substring), reword without adding claims and say so in the report.
- `q9_worksheets.js`, `q10_homework.js` and `q11_extra.js` are generated by `src/gen/`; make the change in the generator and regenerate, never in the generated file.
- When a finding also names a page (guide, reference, tell-apart), fix the same wording there.

Then run the gates from `src/`, in this order, and fix anything they report:

```
cd src && python3 build.py && node test.js && node style_check.js && node render_test.js && node step_check.js && LIMIT=600 node explain_check.js
python3 review_test.py
python3 browser_test.py
python3 sweep_test.py
python3 stepper_test.py
python3 problemset_test.py
python3 equation_test.py
```

`build.py` and every check read and write the one built file in `/mnt/user-data/outputs/`. When another worktree can build at the same time, run each build together with the checks that read it under one lock, for example `flock <lock file> sh -c 'python3 build.py && node test.js && ...'`.

No pull requests. Commit to `main` and push the work branch only when the user asks. Reply in under 200 words: findings applied, findings not applied and why, and the gate results verbatim.
